# 并发控制中的封锁协议

数据库并发控制（Concurrency Control）的核心目标是在允许多个事务同时访问共享数据的前提下，保证数据库的一致性和隔离性。**封锁（Locking）** 是最基本、最广泛的并发控制机制，通过引入**共享锁（Shared Lock, S-lock）**和**排他锁（Exclusive Lock, X-lock）**来协调事务对数据对象的访问冲突。下面从三个维度系统阐述封锁协议的理论框架。

---

## 一、保证数据一致性的三级封锁协议

三级封锁协议（Three-Level Locking Protocol）在排他锁（X锁）与共享锁（S锁）的相容矩阵基础上，通过逐步增强锁的持有约束，依次解决**丢失修改（Lost Update）**、**读脏数据（Dirty Read）**和**不可重复读（Non-repeatable Read）**三类数据不一致问题。

### 1. 一级封锁协议（1° Protocol）

**规则：** 事务 \(T\) 在修改数据对象 \(R\) 之前必须先对 \(R\) 施加 **X锁**，直到**事务结束**（提交或回滚）时才释放。

**解决的不一致：** 防止**丢失修改**。由于写操作被 X锁 互斥，任何时刻只有一个事务能修改 \(R\)。

**未解决：** 读脏数据、不可重复读。因为读操作不需要加锁，事务可以读取未提交的脏数据。

### 2. 二级封锁协议（2° Protocol）

**规则：** 满足一级封锁协议，且事务 \(T\) 在读取 \(R\) 之前必须先对 \(R\) 施加 **S锁**，**读完后即可释放**。

**解决的不一致：** 防止丢失修改和读脏数据。因为读取时加 S锁，写事务的 X锁 会被阻塞；且 S锁 在读取后立即释放，写事务无需长期等待读事务。

**未解决：** 不可重复读。由于 S锁 过早释放，同一事务内再次读取 \(R\) 时，可能已被其他事务修改。

### 3. 三级封锁协议（3° Protocol）

**规则：** 满足一级封锁协议，且事务 \(T\) 在读取 \(R\) 之前必须先对 \(R\) 施加 **S锁**，直到**事务结束**才释放。

**解决的不一致：** 同时防止丢失修改、读脏数据和不可重复读。长事务内多次读取同一数据时，S锁 的持有保证了其他事务无法修改该数据。

**局限性：** 三级封锁协议不能防止**幻读（Phantom Read）**。幻读涉及范围内数据的插入与删除，需通过更高隔离级别（如可串行化）或多版本并发控制（MVCC）解决。

## 二、保证并行调度可串行性的两段锁协议

**可串行性（Serializability）** 是并发调度正确性的形式化标准。两段锁协议（Two-Phase Locking Protocol, 2PL）是实现冲突可串行化（Conflict Serializability）的**充分条件**。

### 核心定义

事务对数据对象的加锁与解锁操作划分为两个严格时序阶段：

1. **扩展阶段（Growing Phase / Locking Phase）：** 事务可以**获取**新锁，但**不得释放**任何锁。
2. **收缩阶段（Shrinking Phase / Unlocking Phase）：** 事务可以**释放**锁，但**不得获取**任何新锁。

### 关键定理

> **若并发执行的所有事务均遵守两段锁协议，则它们的任何并发调度都是冲突可串行化的。**

该定理保证了调度结果与某一串行执行序列等价，从而确保数据库状态的一致性。

### 重要性质与局限

- **充分非必要条件：** 并非所有可串行化调度都要求事务遵循 2PL。但遵循 2PL 的事务集合，其并发调度必然可串行化。
- **死锁风险：** 2PL 本身**不保证不发生死锁**。多个事务在扩展阶段相互等待对方持有的锁，极易形成循环等待链。
- **级联回滚（Cascading Rollback）：** 若事务在收缩阶段过早释放写锁，其他事务可能读取其未提交的结果；一旦该事务回滚，已读取这些脏数据的事务也必须级联回滚。**严格两阶段锁（Strict 2PL）** 和 **保守两阶段锁（Rigorous 2PL）** 通过将写锁持有到事务结束来避免此问题。

## 三、避免死锁的封锁协议

死锁（Deadlock）是并发封锁中无法回避的固有风险。当两个或多个事务相互持有对方所需的锁并无限等待时，即形成死锁。其产生的四个必要条件为：**互斥条件**、**占有等待条件**、**不可剥夺条件**、**循环等待条件**。避免死锁的封锁协议通过破坏后三个条件之一来预防死锁。

### 1. 一次封锁法（One-Shot Locking / Preclaiming）

**机制：** 事务在**开始前**一次性将所有需要访问的数据对象全部加锁；若任一锁请求失败，则事务等待，且不占有任何锁。

**破坏的条件：** 占有等待（Hold and Wait）。

**优点：** 从根本上杜绝死锁。

**缺点：** 
- 并发度显著降低，事务独占大量锁资源，造成资源利用率下降。
- 难以在事务开始时准确预知所有需要访问的数据对象。

### 2. 顺序封锁法（Ordered Locking / Hierarchical Locking）

**机制：** 系统对所有数据对象预设一个全局的**封锁顺序（Lock Ordering）**，所有事务必须严格按照此顺序申请锁。

**破坏的条件：** 循环等待（Circular Wait）。

**优点：** 适用于数据结构相对稳定的系统。

**缺点：**
- 难以动态确定所有封锁对象及其顺序，尤其是涉及范围查询或动态索引时。
- 实现复杂，维护全局顺序的开销大。

### 3. 超时与死锁检测（工程实践中的补充）

虽然不属于严格的"死锁避免协议"，但在工程实践中：
- **超时法（Wait-Die / Wound-Wait）：** 基于事务时间戳的优先级策略，老事务等待新事务（Wait-Die）或新事务被回滚（Wound-Wait），确保无循环等待。
- **等待图法（Wait-For Graph）：** 数据库系统维护事务-锁的等待图，定期检测是否存在环路；若发现环路，则选择代价最小的事务进行**剥夺（Preemption）**与回滚，解除死锁。

## 总结对比

| 协议类型 | 核心目标 | 关键机制 | 主要保障 | 未解决问题 |
|---------|---------|---------|---------|-----------|
| **一级封锁** | 数据一致性 | 修改前加X锁，事务结束释放 | 防止丢失修改 | 读脏、不可重复读 |
| **二级封锁** | 数据一致性 | 一级 + 读前加S锁，读完释放 | 防丢失修改、读脏 | 不可重复读 |
| **三级封锁** | 数据一致性 | 一级 + 读前加S锁，事务结束释放 | 防丢失修改、读脏、不可重复读 | 幻读 |
| **两段锁（2PL）** | 调度可串行性 | 加锁与解锁分两段 | 冲突可串行化 | 死锁、级联回滚 |
| **一次封锁法** | 死锁避免 | 事务开始前一次性加全部锁 | 无死锁 | 并发度低、难预知数据 |
| **顺序封锁法** | 死锁避免 | 全局顺序加锁 | 无死锁 | 实现复杂、动态对象难排序 |

三级封锁协议与两段锁协议属于不同维度的设计：前者聚焦于**隔离级别的数据一致性**，后者聚焦于**调度的正确性**；实际数据库系统（如 MySQL InnoDB、PostgreSQL）通常将两者结合，在 2PL 框架下根据隔离级别动态选择锁的持有策略。
